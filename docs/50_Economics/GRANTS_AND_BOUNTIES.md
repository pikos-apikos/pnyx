# GRANTS_AND_BOUNTIES

## 1. Purpose

This document defines how the system uses grants, bounties, and related incentive instruments.

Its purpose is to ensure that programmatic funding:
- expands public capacity,
- supports challenge and experimentation,
- rewards useful work,
- does not quietly buy governance outcomes,
- does not privilege operator comfort over civic need,
- remains auditable, bounded, and politically legible.

This document complements:
- `FUNDING_MODEL.md`
- `TREASURY.md`
- `PUBLIC_IP_MODEL.md`
- `SKILL_ECONOMICS.md`
- `SKILL_EVALUATION.md`
- `POLITICAL_ECONOMY.md`
- `MINIMUM_VIABLE_PNYX.md`

Grants and bounties are not neutral instruments.
They shape what work gets done, who can afford to do it, and what kinds of actors become central.

---

## 2. Core Principle

Grants support capacity.
Bounties reward bounded deliverables.

Neither grants nor bounties may buy:
- governance legitimacy,
- constitutional authority,
- routing outcomes,
- classification leniency,
- immunity from challenge,
- default status without evaluation.

The correct order is:

**public need -> funding instrument -> bounded work -> public return**

Not:

**available money -> preferred actor -> hidden political leverage**

---

## 3. Instrument Types

The system distinguishes at least the following instruments:

### 3.1 Grants
Time-bounded support for:
- capacity building,
- maintenance,
- evaluation infrastructure,
- commons development,
- access and translation,
- local civic coordination,
- challenge capacity,
- research and learning.

### 3.2 Bounties
Rewards for clearly defined deliverables such as:
- a benchmark suite,
- a migration adapter,
- a translation layer,
- a challenge tool,
- a packet formatter,
- a security fix,
- a public audit projection,
- a local pilot kit.

### 3.3 Fellowships or Stipends
Temporary support for sustained contributors in thin-capacity areas.

### 3.4 Matching Support
Treasury amplification of community-led support under defined rules.

### 3.5 Prize Programs
Structured competitions for public-interest outputs, where appropriate.

Each instrument carries different capture risks and should not be treated as interchangeable.

---

## 4. Why Distinguish Grants from Bounties

A grant is appropriate when:
- the work is exploratory,
- capacity must be sustained over time,
- the public benefit is diffuse,
- maintenance matters,
- exact outputs cannot be fully specified upfront,
- underrepresented or local actors need runway.

A bounty is appropriate when:
- the deliverable can be specified,
- acceptance criteria can be stated,
- public return is clear,
- multiple actors can reasonably compete,
- the work can be evaluated against bounded conditions.

Using a bounty where a grant is needed creates metric gaming.
Using a grant where a bounty is enough creates favoritism risk.

---

## 5. Eligible Grant Areas

Grants may support:
- skill commons creation,
- skill evaluation and regression infrastructure,
- challenge and appeals capacity,
- accessibility and translation,
- local participation tooling,
- benchmark commons,
- protocol adapters,
- public documentation,
- public civic education materials,
- underrepresented group access support,
- public IP maintenance,
- migration and portability work,
- political-economy research relevant to system fairness.

Grant areas should be public, enumerated, and periodically reviewable.

---

## 6. Eligible Bounty Areas

Bounties may support:
- specific software modules,
- benchmark fixtures,
- adversarial test sets,
- packet validation tools,
- classification rule validators,
- audit-view components,
- public IP compatibility adapters,
- migration utilities,
- translation bundles,
- issue-specific local kits,
- protocol conformance tools,
- incident-response tooling,
- documentation upgrades tied to concrete acceptance criteria.

Bounties should be used for work that can be validated without aesthetic favoritism.

---

## 7. Ineligible Uses

Grants and bounties may not be used to:
- buy votes,
- reward favorable governance positions,
- purchase classification outcomes,
- privilege one route outcome over justified routing,
- silence critics,
- finance hidden lobbying inside the civic loop,
- subsidize operator discretion without scrutiny,
- create exclusive rights over commons-core outputs,
- make donor-aligned actors effectively irreplaceable.

If an instrument does these things, it is not civic support.
It is soft capture.

The same firewall applies to participant compensation
(`FUNDING_MODEL.md` §21.1; `TREASURY.md` §12):
payment for civic participation time must be declared in advance,
equal or transparently differentiated,
and independent of the participant's position, vote, or the final decision.

---

## 8. Funding Source Linkage

Every grant or bounty program must disclose:
- funding source category,
- treasury partition,
- whether donor restrictions apply,
- whether public matching applies,
- whether the output becomes public commons,
- whether contributor compensation includes future revenue share,
- whether the work is bootstrap-critical.

No program may hide influence by pretending to be “just implementation support.”

---

## 9. Public Return Requirement

Every grant or bounty must produce a public return statement.

That statement should answer:
- what is being funded,
- who benefits,
- what becomes public,
- what remains private if anything,
- how the work is challengeable,
- how success will be checked,
- whether the result enters the commons,
- whether the result affects future dependency.

Public money or civic fundraising should not yield vague goodwill.
It should yield visible public capacity.

---

## 10. Grant Structure

Each grant should define:
- purpose,
- duration,
- eligible recipients,
- reporting expectations,
- public return expectations,
- milestones where appropriate,
- spending restrictions,
- evaluation or review criteria,
- renewal rules if any,
- closure conditions.

Grants should prefer bounded duration over indefinite dependence.

Renewals must be explicit and reviewable.

---

## 11. Bounty Structure

Each bounty should define:
- bounty target,
- scope,
- acceptance criteria,
- evaluation method,
- deadline or window,
- award amount or band,
- whether split awards are allowed,
- public licensing expectations,
- who evaluates completion,
- what happens if no submission meets the threshold.

A bounty without acceptance criteria is a reputation contest.

---

## 12. Evaluation and Acceptance

Grant completion and bounty acceptance must not depend on one opaque actor.

Acceptance should include as appropriate:
- rule-based validation,
- benchmark or task checks,
- packet or protocol conformance checks,
- reviewer plurality,
- public artifact inspection,
- challenge window,
- human review for high-consequence outputs.

A valid deliverable is not the same thing as a politically comfortable deliverable.

---

## 13. Commons Bias

The system should prefer grants and bounties that strengthen the commons.

Examples:
- open benchmark fixtures,
- public challenge tools,
- migration adapters,
- accessibility assets,
- shared evaluation harnesses,
- local reuse kits,
- open packet scaffolds.

Where non-open outputs are funded, the public rationale and return logic must be stronger.

Commons bias is an anti-capture rule, not an aesthetic preference.

---

## 14. Contributor Diversity and Access

Program design must consider who can realistically compete for grants and bounties.

Without care, programs will favor:
- already networked actors,
- technical insiders,
- high-status contributors,
- people with free time,
- organizations with proposal-writing capacity.

The system should therefore consider:
- small-grant tracks,
- lightweight application paths,
- local or language-specific windows,
- underrepresented-community eligibility boosts,
- public templates for proposals,
- mentorship or pairing where appropriate.

Open competition alone does not guarantee fair access.

---

## 15. Challenge Capacity Must Be Funded

A healthy system funds not only builders but challengers.

Grant and bounty programs should reserve support for:
- adversarial review,
- minority-view tooling,
- challenge interfaces,
- watchdog analysis,
- audit usability,
- capture detection,
- translation of critiques.

A system that pays for production but not contestation subsidizes its own blind spots.

---

## 16. Relationship to Skills

Where grants or bounties affect the skill layer, they must respect:
- skill tiering,
- evaluation requirements,
- registry independence,
- no automatic default status,
- no inference that funding equals public trust.

Examples:
- a grant may fund a Tier 1 template series,
- a bounty may fund a benchmark harness,
- a grant may support a challenger skill line,
- a stipend may support maintenance of evaluation infrastructure.

But a funded skill remains only as trusted as its evaluation evidence.

---

## 17. Relationship to Public IP

Outputs funded through grants or bounties must declare:
- authorship,
- stewardship,
- licensing posture,
- public IP class if applicable,
- revenue eligibility if applicable,
- public-return routing if applicable.

By default, publicly funded outputs should favor public IP commons logic.

If exclusivity or restricted licensing is proposed, the scrutiny threshold must rise.

---

## 18. Renewal and Dependency Risk

Recurring grants may create healthy continuity or unhealthy dependence.

The system must track:
- grant renewal frequency,
- concentration by recipient,
- structural dependence on one grantee,
- whether renewal is funding maintenance or funding inertia,
- whether funded work is still publicly valuable,
- whether alternatives can realistically emerge.

Long-running grants should face periodic review.
Otherwise grants become hidden tenancy.

---

## 19. Bounty Gaming Risks

Bounties may fail through:
- metric gaming,
- lowest-effort compliance,
- fragmentation of maintenance responsibility,
- over-optimization for acceptance criteria,
- superficial “winner” artifacts with poor long-term value,
- exclusion of less resourced actors.

To reduce this, bounties should:
- use bounded but meaningful acceptance criteria,
- define maintenance expectations where relevant,
- allow no-award outcomes,
- preserve public inspection,
- avoid rewarding only speed.

A bounty should not train the ecosystem to optimize for clever demos over civic durability.

---

## 20. Grant Capture Risks

Grants may fail through:
- insider favoritism,
- vague success criteria,
- political patronage,
- symbolic diversity without real access,
- hidden alignment pressure,
- renewal dependency,
- funding comfort over challenge.

To reduce this, grants should:
- publish clear purposes,
- publish recipient rationale,
- disclose source restrictions,
- preserve public-return requirements,
- remain challengeable,
- avoid automatic renewal.

---

## 21. Program Governance

Every grant or bounty program should define:
- who launches it,
- who funds it,
- who evaluates outputs,
- who handles disputes,
- who records the audit trace,
- who closes or renews it,
- how conflicts of interest are handled.

No single actor should silently control the full lifecycle of a funding program.

Bootstrap may have thinner separation,
but every concentration must be named as program governance debt.

---

## 22. Treasury Routing

All grant and bounty flows must be treasury-routed.

This includes:
- source partition,
- allocation decision,
- release schedule,
- milestone linkage,
- recapture or clawback rules if any,
- closure record,
- public-return record.

No side payments, informal sponsorships, or off-ledger compensation may shape civic-critical programs.

---

## 23. Public Views and Auditability

The public should be able to inspect, at minimum:
- active programs,
- funding source class,
- purpose,
- recipient class or recipient where appropriate,
- amount or band,
- commons status of outputs,
- acceptance status,
- challenge status,
- renewal status,
- concentration indicators.

Readable program views must remain linked to canonical treasury and audit traces.

---

## 24. Bootstrap Profile

Bootstrap should favor:
- small, bounded grants,
- simple bounty formats,
- strong commons bias,
- funding for challenge capacity from the start,
- public templates for applicants,
- explicit no-default-without-evaluation rule,
- low administrative overhead,
- visible source dependence.

Bootstrap should avoid:
- prestige-heavy fellowships with weak output logic,
- giant bounty hype cycles,
- opaque discretionary programs,
- dependence on one patron to fund all public work,
- assuming program complexity equals seriousness.

Bootstrap program design should be narrow, legible, and survivable.

---

## 25. Failure Signals

The following indicate likely distortion or capture:

- the same actors repeatedly win all major programs,
- challenge and watchdog work remains underfunded,
- bounty criteria reward performative compliance,
- grants renew without serious review,
- funded outputs become de facto proprietary,
- application burden excludes ordinary or local contributors,
- funding follows visibility rather than civic need,
- source restrictions quietly shape program priorities,
- funded skills are treated as default before evaluation,
- nobody can explain the public return in concrete terms,
- compensation for participation correlates abnormally with participant positions.

Repeated failure signals require redesign, not only better administration.

## 27. Closing Principle

Grants and bounties are useful because they convert intention into organized work.

They are dangerous because they also convert money into priority.

The system must therefore use them in a way that:
- builds capacity,
- rewards useful contribution,
- preserves challenge and dissent,
- strengthens the commons,
- and keeps funding power from quietly becoming governance power.

The point is not to stop paying for work.
The point is to ensure that paid work still serves a public constitution.
