# BOOTSTRAP_REALITY_CHECK

> **Note:** This document has been updated to reflect the normative rules in [SYSTEM_PATCH_v2](../99_Reference/SYSTEM_PATCH_v2.md).

## 1. Purpose

This document defines the realism constraints of the bootstrap phase.

Its purpose is to prevent the system from confusing:
- specification completeness with implementation readiness,
- rhetorical ambition with operational capacity,
- first enthusiasm with sustainable adoption,
- documented safeguards with demonstrated effectiveness.

The bootstrap phase must be judged not by how sophisticated the full design appears,
but by whether a small team can run a bounded prototype honestly, repeatedly, and usefully.

This document complements:
- `MINIMUM_VIABLE_PNYX.md`
- `PROTOTYPE_PLAN.md`
- `CONSTITUTIONAL_BOOTSTRAP.md`
- `COMMUNITY_FORMATION.md`
- `FUNDING_MODEL.md`

Bootstrap realism is not pessimism.
It is anti-delusion.

## 2. Core Principle

Bootstrap must be smaller than the specification.

The full design may remain the constitutional horizon,
but the bootstrap runtime must be constrained by:
- team size,
- time,
- budget,
- attention,
- technical maturity,
- community patience,
- operational fragility,
- and the real cost of maintaining trust.

The bootstrap phase fails when it tries to prove the entire theory at once.

---

## 3. What Bootstrap Must Prove

Bootstrap does **not** need to prove:
- full legitimacy,
- constitutional completeness,
- national scalability,
- final anti-capture success,
- full treasury design,
- full cryptographic identity,
- production emergency automation.

Bootstrap **does** need to prove at least the following:

1. a bounded group will use the system on a real issue,
2. the packet is more useful than the group's current informal process,
3. challenge and revision happen visibly,
4. the skill layer can be improved through evaluation,
5. the operators can remain visible and bounded,
6. the system can survive more than one cycle without collapsing into theater.

If bootstrap cannot prove these things, the rest is irrelevant.

---

## 4. Bootstrap Assets Inventory

Every bootstrap attempt should begin by naming its real assets.

At minimum, the project should inventory:

- founding people available,
- weekly hours realistically available,
- technical skills available,
- facilitation skills available,
- community access already present,
- budget actually secured,
- model/runtime capacity available,
- hosting/infrastructure available,
- legal or organizational shelter if any,
- willingness of a real pilot community.

Bootstrap should be described from these actual assets,
not from ideal future assumptions.

---

## 5. Bootstrap Constraints Inventory

Bootstrap must also name its hard constraints.

These often include:
- no proven public legitimacy,
- no mature evaluation corpus,
- no broad provider diversity,
- human expert scarcity,
- evidence retrieval complexity,
- jurisdiction mapping cost,
- source validation overhead,
- ranking cold-start problems,
- benchmark curation burden,
- revalidation governance burden,
- tradeoffs between legitimacy and throughput,
- overlapping roles,
- limited challenge participation,
- low budget,
- untested retention,
- weak institutional trust,
- high founder dependence,
- limited implementation bandwidth.

Constraints are not embarrassing.
Unstated constraints are dangerous.

---

## 6. Realistic Team Shape

A realistic bootstrap team is small.

Typical viable bootstrap roles include:
- 1 runtime/product integrator,
- 1 backend or systems implementer,
- 1 skill/evaluation person,
- 1 civic process and facilitation person,
- 1 part-time operator/auditor function.

In some teams, one person may cover more than one role.
If so, role concentration must be named openly.

A bootstrap plan that assumes a large, highly differentiated institutional structure from day one is fictional.

---

## 7. Realistic Time Budget

Bootstrap must be planned in time units, not aspiration.

A team should state:
- expected hours per week,
- expected duration of prototype phase,
- what happens if availability drops by half,
- who is replaceable and who is a single point of failure,
- how much time is needed per advisory cycle,
- how much time challenge and review actually cost.

If time is not budgeted, complexity will silently default to founder burnout.

---

## 8. Realistic Money Budget

Bootstrap must state:
- actual available budget,
- minimum viable operating budget,
- one-time setup costs,
- recurring costs,
- reserve needs,
- what is deferred because of cost,
- what happens if projected funding does not arrive.

At minimum, bootstrap should cost-model:
- model/runtime use,
- storage and logging,
- basic hosting,
- UI/workflow tooling,
- community facilitation,
- evaluation maintenance,
- incident or legal contingency,
- documentation and onboarding.

A bootstrap treasury that exists only conceptually is not a treasury.

---

## 9. Scope Discipline

Bootstrap must be scope-bounded.

The first implementation should be limited by:
- one pilot community,
- one or two issue classes,
- advisory-only outputs,
- narrow state machine,
- fixed skill set,
- fixed challenge path,
- simple audit views,
- low financial surface,
- no irreversible power.

A bootstrap that tries to include:
- production funding infrastructure,
- public IP monetization,
- full cryptographic identity,
- federated verifier networks,
- broad meta-governance,
- large-scale participation,

before proving basic usefulness is almost certainly overbuilt.

---

## 10. Bootstrap Non-Negotiables

Even a narrow bootstrap must preserve certain non-negotiables.

At minimum:
- no silent edits,
- no unlogged operator intervention,
- no active-case retuning,
- visible challenge path,
- visible packet versioning,
- minimum plural skill panel for non-trivial proposals,
- explicit founder/operator role disclosure,
- explicit bootstrap debt disclosure,
- visible limits of the prototype.

These are the minimum honesty conditions of bootstrap.

---

## 11. What Bootstrap Should Explicitly Defer

Bootstrap should explicitly defer anything that is not necessary to answer first-cycle questions.

Common deferrals:
- production treasury automation,
- complex matching formulas,
- public IP revenue routing,
- full constitutional amendment mechanics,
- advanced emergency cryptographic enforcement,
- full identity and verifier subsystem,
- comprehensive local federation,
- high-complexity procurement layers,
- large benchmark universes,
- full market/state execution machinery.

Deferral is a sign of seriousness.
Pretending readiness is not.

---

## 12. Bootstrap Assumptions Register

The project should maintain a `BootstrapAssumptionsRegister`.

Each assumption should state:
- the assumption,
- why it matters,
- what evidence currently supports it,
- how it will be tested,
- what happens if it fails.

Typical assumptions include:
- a pilot group will return for a second cycle,
- five-skill packets are not too cognitively heavy,
- challenge will be used by real participants,
- a small team can maintain the evaluation loop,
- the prototype will remain understandable,
- at least one issue domain will produce visible utility.

Assumptions without tests become ideology.

---

## 13. Bootstrap Debt Register

Bootstrap should maintain a `BootstrapDebtRegister` distinct from normal technical debt.

Bootstrap debt includes:
- role concentration,
- provider concentration,
- model monoculture,
- weak external review,
- thin challenge capacity,
- founder narrative dependence,
- incomplete community diversity,
- missing automation,
- simplified treasury controls,
- incomplete legal shelter.

Bootstrap debt must be:
- named,
- logged,
- ranked,
- re-evaluated after every pilot cycle.

Unnamed bootstrap debt becomes permanent structure.

---

## 14. Go / No-Go Gates

Bootstrap should use explicit gates rather than continuous drift.

### 14.1 Build Gate
Before implementation begins, confirm:
- a real pilot community candidate exists,
- minimum team exists,
- minimum time exists,
- minimum budget exists,
- minimum runtime scope is reduced.

### 14.2 Pilot Gate
Before closed pilot begins, confirm:
- core loop works internally,
- packet generation works,
- audit visibility works,
- challenge path works,
- operator intervention is visible,
- skill evaluation baseline exists.

### 14.3 Repeatability Gate
Before broader expansion, confirm:
- at least two cycles completed,
- the same or similar community returned,
- challenge was used,
- packet was actually referenced,
- severe failure classes are understood,
- founder load is survivable.

If these gates are not met, the answer is not "scale anyway."
It is "shrink, revise, or pause."

---

## 15. Bootstrap Success Criteria

Bootstrap success should be modest and concrete.

Reasonable success signals include:
- one real community completes more than one cycle,
- packets are used in actual discussion,
- challenge changes something real,
- audit views are understood by non-operators,
- skill regressions are tracked and reduced,
- founders are not required to invisibly rescue every case,
- at least one participant asks to use the system again,
- a second pilot becomes plausible for reasons other than hype.

Success does not require mass adoption.
It requires repeatable usefulness.

---

## 16. Bootstrap Failure Criteria

Bootstrap should be treated as failed, paused, or reset if:
- no real community completes a second cycle,
- challenge paths exist but nobody can or will use them,
- packet usefulness is repeatedly low,
- the same insider group performs all meaningful actions,
- operator intervention is frequent and hidden,
- evaluation decays into taste and intuition,
- the runtime is too complex for the team to maintain,
- the founding group burns out,
- the budget cannot sustain another cycle,
- pilot participants treat the system as an interesting demo but not a useful tool.

Failure is not discrediting.
Failure without stopping is discrediting.

---

## 17. Bootstrap Complexity Budget

The project should treat complexity as a scarce resource.

A bootstrap `ComplexityBudget` may include rough limits on:
- number of services,
- number of live skill classes,
- number of audit views,
- number of user roles,
- number of funding partitions actively used,
- number of states in the live flow,
- number of required manual review surfaces.

When a new feature is proposed, the system should ask:
- what complexity does this add,
- what complexity does it remove,
- and what real bootstrap hypothesis does it help test?

Complexity without test value is vanity.

---

## 18. Cognitive Load Budget

Bootstrap must also respect cognitive limits.

The system should track whether:
- packets are too long,
- challenge instructions are too complex,
- users can distinguish disagreement from indecision,
- participants understand what changed between versions,
- audit surfaces remain readable.

A system that is procedurally correct but cognitively unusable has failed bootstrap.

---

## 19. Founder Dependence Check

Bootstrap should repeatedly ask:

- If one founder disappears, what stops?
- If one operator disappears, what stops?
- If one community facilitator disappears, what stops?
- If one model provider disappears, what stops?
- If one donor disappears, what stops?

A bootstrap that cannot survive any single departure is not stable enough for rhetorical expansion.

---

## 20. Bootstrap and AI Dependence

Bootstrap must explicitly state:
- which models are being used,
- whether diversity is real or nominal,
- which skills are model-dependent,
- where epistemic monoculture may be present,
- what happens if one model family fails,
- how critic loops reduce but do not eliminate shared blind spots.

Bootstrap should not overclaim cognitive plurality because it has multiple prompts.

---

## 21. Bootstrap and Community Fit

The project should not say "the community failed."
It should ask:
- was the pilot community a good fit,
- did it have a recurring proposal pain,
- did it have enough patience,
- did it have enough real stake,
- was the packet solving a real problem,
- was the challenge path too demanding,
- did founders choose for prestige rather than fit?

Bad community fit is a bootstrap design failure, not just a user problem.

---

## 22. Bootstrap and Funding Reality

Bootstrap should assume:
- fundraising will be slower than hoped,
- donor concentration risk will appear early,
- small recurring contributions are hard to build,
- challenge and access work are easy to underfund,
- reserves are more important than symbolic scale.

If bootstrap needs perfect future funding to survive, it is not a viable bootstrap.

---

## 23. Bootstrap and Repetition

Bootstrap should prefer repetition over expansion.

The key question is:
- can the same loop run again with less confusion and less founder rescue?

Second-cycle success is often more informative than first-cycle excitement.
Third-cycle success is often more informative than new-user attention.

Bootstrap that scales before repeating is usually avoiding learning.

---

## 24. Operational Review Discipline

After every pilot cycle, bootstrap should ask:
- what was genuinely useful,
- what was performative,
- what required hidden manual rescue,
- which invariant came under pressure,
- which subsystem was unnecessary,
- which subsystem is still missing,
- what should be removed,
- what must be coded next,
- what remains only prose,
- whether the project deserves another cycle.

Review must be brutally honest.
Bootstrap optimism is abundant by default.

---

## 25. Minimum Bootstrap Outputs

A serious bootstrap should produce, at minimum:
- one real packet set,
- one challenge log,
- one operator intervention log,
- one skill evaluation report,
- one pilot retrospective,
- one bootstrap debt update,
- one assumptions update,
- one go/no-go decision record.

Without these outputs, bootstrap is storytelling.

---

## 26. Stop, Reset, or Continue

Bootstrap decision options should be explicit:

### Continue
When the prototype is useful, bounded, and survivable.

### Continue with Simplification
When some value exists but the current runtime is too heavy.

### Pause
When signal is unclear and the team needs time or reduction.

### Reset
When the wrong pilot, wrong scope, or wrong architecture profile was chosen.

### Stop
When no real community value appears, or when the cost of another cycle exceeds the evidence for continuing.

A mature bootstrap treats stopping as an allowed result.

## 28. Closing Principle

Bootstrap is credible only when it is willing to be smaller than its own theory.

The real bootstrap question is not:
- How complete is the specification?

It is:
- Can a small team, with limited time and money, help one real community on one real problem, twice, without lying about what the system can do?

If the answer is no, the correct move is not more grandeur.
It is less system, more reality.
